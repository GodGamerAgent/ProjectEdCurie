# EdCurie

## Run

This is a single React/Vite and Express application using the Replit PostgreSQL database. The Replit workflow runs `npm run dev` on port 5000. Run `npm run db:migrate` to apply the checked-in Drizzle migrations to the development database. The application does not create tables or seed records at startup. For Replit-managed production databases, use the Publish flow to apply schema changes; do not run development migrations against production.

`npm run build` checks the frontend build and TypeScript. `npm run test:isolated` starts a temporary local PostgreSQL instance, applies the migrations there, runs the foundation tests, and removes the temporary instance afterward. It does not use the development or production database.

## First administrator and institute setup

1. Replit-managed Clerk must have a supported email sign-in method that verifies the actual primary email address. The development and published environments have separate identity stores.
2. In Replit Secrets, set `EDCURIE_BOOTSTRAP_ADMIN_EMAIL` to the first platform administrator's email. It may be a personal email; no institute or approved domain is required. Never put the address or credentials in source code. Without this secret and the provisioned Clerk keys, app sign-in remains unavailable.
3. Sign in as that administrator and complete Clerk's primary-email verification. The server grants the first administrator role only when the verified email matches the configured bootstrap email and no administrator already exists. If another account already holds that role, setup reports a conflict rather than creating a second administrator.
4. In the administrator workspace, create each institute with its display name and optional logo, then approve its actual email domains and invite teachers using their exact addresses. There is no preconfigured institute or example domain. Teacher roles are granted only to explicitly invited addresses. Students also need an approved verified email and enrollment in a course at their institute.
5. Verify sign-in with a real institute account in each environment. A domain match alone never verifies ownership. Live institute sign-in remains unverified until tested with a real account.

The institute migration is additive and does not delete legacy records. Previously existing domains, invitations, users, and courses are left unassigned rather than being guessed into an institute; they cannot grant institute-scoped access until deliberately associated. Adding an existing unassigned domain to an institute assigns that domain, and verified students on it can be associated on their next sign-in. A legacy teacher must be explicitly invited again for the correct institute, which also associates any existing unassigned invitation. Existing unassigned courses require an explicit administrator migration before they can be used; do not bulk-assign them without checking their ownership.

Course resources, assessment eligibility, and file downloads are checked against server-side teacher assignments or student enrollments. Resources are stored in PostgreSQL; PDF and text uploads are limited to 8 MB. A teacher can review extracted page-labelled text or supply manual text after an extraction failure. Publishing a usable resource and a baseline with at least one valid question linked to published usable material in the same course opens onboarding for an enrolled student.

## Student study loop

The current study loop uses the server-side `GROQ_API_KEY` Replit Secret and the Groq model `qwen/qwen3.8-27b` by default. `GROQ_MODEL` optionally overrides the model name. Without the key, requesting a lesson displays an actionable setup message; the administrator workspace reports whether the key is configured without revealing it. Groq receives only the selected concept's published, usable course excerpt and the student's selected tutoring preferences/format. Source IDs and page/section references in responses are checked against the excerpts before they are shown; students can open the cited section through the authorized API.

1. Run `npm run db:migrate` for the additive development schema. Existing accounts, courses, and records are not seeded or replaced. Use the Publish flow for the managed production schema.
2. As an assigned teacher, create a course and enroll the student. Upload and review a PDF or text resource, publish it, and create concepts linked to that resource. Add prerequisite links if needed; cycles are rejected.
3. Create a baseline assessment with objective questions and expected answers, linking questions to concepts. Publish it, then create two teacher-authored practice variations for a concept. Each problem is linked to a baseline source question and has three progressive hints. In **Link an independent twin**, select the original and its distinct same-concept twin. The teacher is responsible for confirming that the variation assesses the same reasoning skill.
4. As the enrolled student, save a goal and availability even before resources are ready. Complete the baseline when the course is ready. Objective answers are matched after trimming, whitespace normalization, and case folding. Active baseline sessions and answers survive refresh; a retry returns the existing result without duplicate evidence. A started assessment can be resumed/submitted from its saved question snapshot while enrollment remains valid, even if the teacher later unpublishes the course material.
5. Open a concept, choose an explanation style, request a source-cited lesson, and open the cited section. Answer a teacher-approved practice question, then check mastery and the assigned teacher's progress view. Test hints, the supported walkthrough after three hints, a fresh independent teacher-authored problem, and a prerequisite diagnostic with a wrong answer. Private goals, preferences, and prior tutor lessons are not shown in teacher progress.
6. After submitting the original problem, choose **Solve linked twin**. The twin is excluded from ordinary practice and diagnostics. Its first exposure must be through this follow-up; previously seen variations cannot be reused as fresh evidence. Answering without hints records `kind=twin`, `assisted=false`; requesting any twin hint records assisted evidence instead. The original problem's hints do not affect this classification. Refreshing and choosing **Resume linked twin** restores consumed hints; retries reuse the same session/result and cannot duplicate evidence.

`npm run test:isolated` verifies these flows in a temporary PostgreSQL instance, with a simulated Groq response; it does not verify a real Groq call. For live verification, add `GROQ_API_KEY` in Tools > Secrets, use actual published course material and a real enrolled institute account, and repeat the steps above. Teacher upload, student walkthrough, and live Groq availability remain unverified until those real steps are completed.

## Continue implementation

`ACCEPTANCE-CHECKLIST.md` maps the original 22 study features and the institute/teacher workflows to current implementation and verification status. It is the continuation record: the first objective-baseline → cited Groq lesson → teacher-approved independent practice → mastery loop is implemented and covered in isolated tests. The development database has had only additive migrations applied; no fixture data was seeded.

The learning loop includes source-grounded checks, prerequisite diagnosis, focused practice, linked twins, and conservative mastery. Teachers set class times/estimates; students set private availability/commitments. Plans recalculate after evidence or missed sessions while preserving deadlines and completed blocks. FSRS-7 reviews feed hint-free recall into mastery; adaptive mocks keep scores separate. Assignments support text/PDF attachments, structured categories, and optional concept-linked teacher evidence outside mastery. Teachers have course activity summaries and authorized learner timelines. Students can save/delete intake context, track private dated milestones, and rate explanations; captured feedback suggests formats after enough ratings. Completed focus blocks contribute active minutes to lesson context. Browser speech, focus/break timers, and idempotent XP are available; leaderboard opt-in is off by default and hides emails. Next connect milestones to study plans, then extend tutoring and mocks. Live Groq, voice support, and real-account walkthroughs remain unverified. Do not add sample users, courses, materials, attempts, or metrics to development or production. Browser testing that needs Clerk must be done by the owner using their real account; no publicly reachable test-login bypass is supported.

For timetable setup, a teacher opens the course study workspace and adds a weekly class with an IANA timezone, weekday, date range, and local start/end time. Use **Cancel date** for a skipped occurrence or **Cancel series** to end the recurring entry. An enrolled student can save multiple weekly availability windows and one-off personal commitments in that course's study workspace. Those personal titles and times are returned only to that student; course teachers can see shared class times only.
